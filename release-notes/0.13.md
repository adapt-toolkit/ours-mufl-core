# core 0.13 — bilateral contact removal + explicit invite modes

Two protocol prerequisites requested ahead of room work. Both are additive and
default-preserving; no existing peer changes behaviour unless it opts in.

## Wire delta

| Surface | Change | Class | OSP impact |
|---|---|---|---|
| `::a2a_messaging::receive_contact_removal` | **NEW** transaction. `$targ` = (`$reason` str+, `$pv` int+). Registry **crm**, single version. | B | none — emission is gated fail-closed, so a pre-0.13 peer is never sent it |
| `a2a_protocol::invite_eph_t` | **+`$m` (`invite_mode_t+`)** — closed ADAPT enum `<$one_time, $public>`. Absent ⇒ one-time. | A | none — older decoders ignore the extra member; `$iv` deliberately NOT bumped |
| `$pv` | `wire_version` 8 → **9** | — | none — every consumer is a `>=` threshold |
| capability | **+`core.contact.removal`** | — | none — absence simply withholds the notice |

Export blob: **+`$contact_origin`** (additive, guarded on import; a pre-0.13 blob
imports unchanged). `pending_invite_t` gains `$mode`/`$created`, both nullable —
and `pending_invites` is reset on import as before, so no migration is needed.

## 1. Bilateral contact removal

`remove_contact` now sends an authenticated notice so the peer drops you too.

- **Cannot be aimed.** The payload carries no target id; the receiver removes the
  channel-authenticated envelope `$from`. A contact can only make you forget *it*.
- **Fail-closed emission**, receipts polarity: positive `core.contact.removal` cap,
  with a caps-silent `contact_pv >= 9` fallback. The receive side is unconditional.
- **Best-effort, never claimed otherwise.** Fire-and-forget, no acknowledgement, and
  not redrivable (the redrive buffer is keyed by the contact you just deleted).
  Returns `$notified` (queued, *not* applied) and `$key_material_retained`.
- **Idempotent / replay-safe**: the operation is "ensure this sender is absent", so
  duplicates, replays, non-contacts and crossed removals all converge and succeed.
- **Routed by `e2e_route`, not forced onto the legacy box.** An epoch-pinned peer is
  notified over the **e2e session** (inner `$contact_removal` marker on
  `receive_e2e_message`, reusing the `$rekey_ping` pattern); an unmigrated pair uses
  the plain `crm`; `downgrade_refused` / `migrating` send nothing (`$notified` FALSE).
- **§5.7 receive-side refusal.** A legacy `crm` from an epoch-pinned contact is a
  downgrade attempt: purge nothing, touch no pin, surface `$downgrade_refused`.
- **Bound control plane, atomic inbound transition.** The outbound refusal is retained;
  inbound, an authenticated `crm` from the bound CP clears the binding via
  `do_disable_monitoring` first, in the same transaction, so no monitoring copy can
  follow it to a peer that is no longer a contact. Both inbound routes share one
  `apply_peer_removal_actions`, so the guard cannot drift between surfaces.
- **Scope of the purge: contact-layer state and queued plaintext ONLY.** This is not a
  hard purge and does not leave "no residue". `purge_contact_state(cid)` uses an
  explicit drop-list (never a `contacts` keep-list, which would also delete peers
  legitimately mid-handshake) and is factored out so a future room-close can call it
  per participant — that caller is NOT in this release.

  **The anti-downgrade pins are RETAINED** (`contact_e2e_seen`, `contact_e2e_epoch`,
  `contact_born_dr`). Removal is peer-triggerable, so clearing them inbound would let a
  peer reaching the legacy channel erase the evidence that forbids it. A pre-review
  revision cleared them on the rationale that retaining them bricks a re-add; **that
  rationale was false and is retracted** — `e2e_route`'s epoch branch returns `"e2e"`
  whenever `peer_has_e2e_bundle` holds, and that reads `peer_ads`, which a re-add
  restores. Only `contact_migration` (transient FSM) and `mig_deferred` (queued
  plaintext) are cleared from that group.

- **Known residual:** the adapt `e2e` library exposes no per-cid session drop, so the
  live Olm ratchet for a removed peer survives in packet state and in exported
  `$e2e_sessions`. Consistent with the long-standing "contacts-layer forget, NOT a key
  wipe" contract; a true wipe needs an upstream toolkit addition. Surfaced as
  `$key_material_retained`.

## 2. Explicit invite modes

`generate_invite` takes the closed ADAPT enum `$mode`: absent or `$one_time` ⇒
**one_time** (unchanged), while `$public` ⇒ a **reusable** invite meant for open
posting. Any other present value is rejected by transaction argument validation.

- The consumption decision reads the **inviter's own** stored mode, never the wire —
  a redeemer cannot promote a one-time invite by editing its copy. The typed wire,
  state, helper and API surfaces all use `invite_mode_t`; only a missing legacy
  value normalizes to `$one_time`.
- **No secret or state is shared between redeemers.** The retained key is the
  inviter's, used only to open leg-1 boxes addressed to it; each redeemer boxes with
  its own fresh ephemeral, leg 3 already mints a fresh inviter ephemeral per
  redemption, and all session state is cid-keyed. A public invite is many independent
  two-party handshakes from one published pubkey.
- A public invite **cannot pre-assign a contact name** (every redeemer would collide
  under it) — refused at `generate_invite`.
- **`revoke_invite`** (idempotent) and **`list_invites`** (readonly, no key material)
  ship with the mode: a never-consumed invite is unsafe without a way to close it.
- **Re-entry boundary (deliberate, not auto-closed).** Removing ONE redeemer does not
  revoke a shared public invite — doing so would cut off every other holder because of
  one removal. So a removed peer CAN re-enter through a still-live public invite; the
  sequence that keeps someone out is `revoke_invite` **then** `remove_contact`. Both
  halves of this are covered by executed assertions. Auto-revoking on removal is left
  as an owner decision, not taken here.
- **Known limitation:** `import_core_state` still resets `pending_invites`, so a public
  invite does not survive a daemon restart and must be re-published. The blocker is
  INV-4 (the ephemeral private key cannot ride the export blob). True perpetuity needs
  either a local-only secret sidecar re-injected at boot, or a secret-free public
  leg 1 — an owner-level security decision, deliberately not taken here. The tool text
  states the limitation rather than implying durability.

## 3. Provenance (substrate only)

`contact_origin` (cid → `$via` / `$invite_id` / `$at`) records how each contact was
admitted — `invite_public`, `invite_one_time`, `invite_redeemed` — and is exposed by
the readonly `list_contact_origins`. Recorded once at first admission and never
rewritten. **Nothing in this core reads it**; it exists so a future trust level can
mark public-invite entrants without having to reconstruct the fact after it is gone.
The trust UI/policy is deliberately NOT implemented.

## Version reconciliation

`version.mm` goes 0.9.0 → **0.13.0**. This is a reconciliation, not a version skip:
the in-code feature-era labels had already reached "core 0.12" while the constant was
last bumped in the 0.9 era. Nothing reads `core_version` to make a decision (it is
exposed informationally by `::a2a_messaging::get_version`), so realigning is safe.

## Tests

New two-node-plus integration suite `packages/core/test/contact-protocol-mufl.test.mjs`
(driver `scripts/test-contact-protocol-mufl.sh`), real packets over a real local
broker, 56 executed assertions.

Functional: one-time single-use preserved, public reuse by distinct redeemers,
per-redeemer working sessions, provenance both sides, revocation + idempotent
revocation, revoked-invite refusal, bilateral removal, third parties unaffected,
repeated removal, crossed removal with zero inbound failures, fail-closed gate against
a capability-limited peer.

Security regressions (two QA-fixture packets, since these need to arrange an epoch pin
and emit hand-built wire shapes no production actor exposes):
- migrated pair — a LEGACY `crm` against an epoch-pinned peer purges nothing and leaves
  the pin state byte-identical, while legitimate removal for that same pair still works
  bilaterally over the e2e route;
- bound control plane — the outbound refusal is retained, an inbound `crm` from the
  bound CP clears the binding, messaging still works afterwards (proving no dangling
  proxy), and no monitoring copy of a later message reaches the removed CP;
- forged/unencrypted `crm` is rejected and removes nobody;
- an invalid invite-mode value is rejected at the closed-enum API/wire boundary,
  while an absent legacy value defaults to `$one_time`;
- the public-invite re-entry boundary, both directions.

No corpus fixture is added for **crm**, matching the **rcp** precedent: both are
class-B, single-version, capability-gated surfaces, and `tests/corpus.mjs` covers
sir/cin/rst/acc/e2e only.
